# 为什么把控制流从 prompt 里搬出来

## 问题的起点

01/02 的单 Agent 循环里，模型用 `finish_reason` 决定"继续调工具"还是"结束任务"。
这个自由度是安全的：最坏情况是多调一次工具，代价几百个 token。

03 章要加 Evaluator。如果照搬同一个模式，编排就只能写在 prompt 里：

```
Planner    -> "请 Executor 执行第 1 步"
Executor   -> "第 1 步做完了，请 Evaluator 评估"
Evaluator  -> "不通过，请 Executor 重做"
Executor   -> ...（谁来判断该重做几次？）
```

这条路能跑通 demo，但有三个结构性问题，而且都不是"prompt 写得不够好"能解决的：

1. **不可测**：没有 LLM 就跑不了任何流程。想验证"评估不通过走哪条分支"，
   每次都要真发请求，还要靠模型配合演出这个分支。
2. **不可控**：模型可以在评估不通过时，自己在文本里写"已通过，进入第 2 步"。
   prompt 里写"请不要这样做"是在请求它，不是在约束它。
3. **不可观测**：出问题时，日志里只有一堆自然语言，分不清是模型判断错了，
   还是编排逻辑错了。

## 分工：Agent 出建议，状态机做裁决

```
                   ┌──────────────────────────────┐
                   │  decide(state, budget)       │  <- 纯函数，零依赖
                   │  5 个动作：                   │
                   │  PLAN / EXECUTE / EVALUATE   │
                   │  / FINISH / ABORT            │
                   └──────────────┬───────────────┘
                                  │ Decision(action, step, reason)
        ┌─────────────────────────┼─────────────────────────┐
        ▼                         ▼                         ▼
   ┌─────────┐              ┌──────────┐              ┌───────────┐
   │ Planner │              │ Executor │              │ Evaluator │
   │ 无工具  │              │ 读写工具 │              │ 只读工具  │
   └─────────┘              └──────────┘              └───────────┘
   产出：Plan               产出：文件 + 汇报         产出：Verdict
   （建议）                 （建议）                  （建议）
```

`decide()` 的判定顺序是刻意排的，不是随手写的 if-else：

| 顺序 | 条件 | 动作 | 为什么放在这个位置 |
|------|------|------|-------------------|
| 1 | 调用数 / token 超预算 | ABORT | 预算必须压过一切，包括"看起来已经做完了" |
| 2 | 还没有计划 | PLAN | |
| 3 | 所有步骤已通过 | FINISH | |
| 4 | 当前步骤 verdict=replan | PLAN | 预算还够才允许 |
| 5 | 有产物、还没评估 | EVALUATE | 产物不可跳过评估 |
| 6 | 重试次数用尽 | PLAN 或 ABORT | 见下面第 2 条不变量 |
| 7 | 默认 | EXECUTE | |

## 三条不变量

**1. 预算是硬约束，verdict 是软建议。**
Evaluator 说 `revise`，但这一步已经重试到上限 —— 此时状态机不"听模型的"，
而是升级为重规划；重规划预算也用完了，就判失败。
模型永远不能覆盖预算，否则"预算"退化成"建议"。

**2. 产物变了，评估立即作废。**
`_do_execute` 里有一行 `step.verdict = None`。少了这行就会出现
"用第 1 次产物的评估结论，去放行第 2 次产物"——这是状态机最容易出的静默错误。

**3. 只有 PASSED 才会被跳过。**
`StepStatus` 只有 `pending` / `passed` 两个值。没有 `failed`：
失败不是一种持久状态，而是一次待裁决的中间态（重试？重规划？终止？）。
多一个"失败状态"，就多一处需要判断"失败之后还能不能救"的分支。

## 工具集是权限边界，不是提示词

| 角色 | 工具集 | 说明 |
|------|--------|------|
| Planner | 无 | 只产出文本，不需要碰文件系统 |
| Executor | `read_file` `write_file` `list_files` | 它要产出文件 |
| Evaluator | `read_file` `list_files` | **它只能看，不能改** |

如果给 Evaluator 写权限，它发现产物不合格时最省事的行为就是**自己动手改**。
一旦它这么做了，"评估"就退化成"自评自改"，多 Agent 的意义消失。

prompt 里写"请不要修改文件"是在请求模型；少给它一个 `write_file` 是在约束模型。
**结构性约束永远优先于提示词约束** —— 这条在 `tests/test_tools.py` 里有断言顶着。

实测这一条是真的起作用：`requirements` 任务里，Evaluator 在最后一步
一轮读了 5 个文件独立核验，全部 4 步的判定都能指出具体依据，不是橡皮图章。
代价是它的 token 消耗和执行器基本相等（见 `02-cost-attribution.md`）。

## 这个选择的验证：故障注入

状态机最大的回报不是"任务成功率更高"，而是**编排的失败路径变得可以断言**。

用真的 LLM 复现这些路径，要么靠运气，要么靠烧钱。用一个 scripted 的假客户端，
它们变成两行代码：

| 用例 | 断言的是什么 |
|------|-------------|
| 评估器永远说 revise | 一定会在有限步内 ABORT，不会死循环 |
| 评估器说 replan | 计划被真的重建，revision +1，然后能跑完 |
| 重规划预算为 0 | 干净地 ABORT，不是无限重规划 |
| Planner 永远返回废话 | 一次格式修复后仍然 ABORT，**不会解析出空计划当成功** |
| `{"steps": []}` | 合法 JSON 但非法计划，同样被拒 |
| 评估器输出不可解析 | 降级为 revise，**绝不默认 pass** |
| verdict 是未知字符串 | 同上，降级为 revise 并留事件 |
| 预算在第 3 次调用爆 | 守卫在调用**之前**抛出，不是花完再说 |
| 一轮里连续调工具 | 单次 dispatch 内超预算同样被拦（守卫挂在每次调用前） |
| decide 被改坏 | `max_iterations` 保险丝兜底，7 步内退出 |
| 带 tool_calls 但 finish_reason=stop | 工具照样执行（01/02 的 `finish_reason` 判断会漏掉） |

全部 73 个测试离线跑完 **0.26 秒**，不吃 API 额度。
这是"把控制流写成代码"的直接回报。

## 这个选择**没有**解决什么

它让编排变得确定、可测、可观测，但**没有让任务更容易成功**。

实测三个任务，多 Agent 的正确率和单 Agent 完全一样，成本是 4.2–9.1 倍
（见 `02-cost-attribution.md`）。状态机的价值在"确定性"，不在"准确率"。

把这两件事混为一谈，是这一章最容易犯的错：
以为"加了 Planner / Evaluator 就更聪明"，实际上只是"流程更可控"。
如果任务本身单 Agent 就能做对，加角色只会让它更贵。
