# 多 Agent 到底贵多少：3 任务 × 2 模式实测

## 实验设置

| 项 | 值 |
|----|-----|
| 模型 | `deepseek-flash`（DeepSeek，OpenAI 兼容协议） |
| 变量 | **只有控制流**：状态机驱动 vs 一条道走到黑 |
| 固定项 | 同一个 `LLMClient`、同一套工具、同一份 `Budget`、同一个 `RunLogger` |
| 单 Agent 基线 | `max_rounds=16`，支持并行工具调用（它确实在用） |
| 预算 | 5 步 / 每步 2 次 / 1 次重规划 / 30 次调用 / 200k tokens |
| 独立验收 | 程序化断言产物内容，**不看 Agent 说了什么** |
| 采样 | 每个组合 1 次（n=1，见文末局限） |

三个任务：

| 任务 | 内容 | 难点 |
|------|------|------|
| `hello` | 创建/追加一个文件 | 几乎不需要规划 —— 用来测**固定开销** |
| `sales` | 读 CSV，按产品汇总销售额，写 Markdown 报告 | 算术精确性 |
| `requirements` | 交叉比对 3 个冲突来源，产出 json + 冲突说明 | 需要裁决规则和跨文件推理 |

复算：`uv run python scripts/report.py`（数据源 `logs/compare_20260923_194900.json`）

## 总览

| 任务 | 模式 | 状态机判定 | 独立验收 | LLM 调用 | tokens | 耗时 | 计划步数 |
|------|------|-----------|---------|---------|--------|------|---------|
| hello | multi | success | PASS | 16 | 16951 | 23.92s | 4 |
| hello | solo | success | PASS | 5 | 4063 | 3.94s | — |
| sales | multi | success | PASS | 22 | 25436 | 22.65s | 4 |
| sales | solo | success | PASS | 3 | 2805 | 2.73s | — |
| requirements | multi | success | PASS | 20 | 30844 | 28.48s | 4 |
| requirements | solo | success | PASS | 3 | 5940 | 7.72s | — |

## 归因

| 任务 | Planner | Executor | Evaluator | 合计 |
|------|---------|----------|-----------|------|
| hello | 838 (5%) | 7280 (43%) | 8833 (52%) | 16951 |
| sales | 947 (4%) | 12679 (50%) | 11810 (46%) | 25436 |
| requirements | 1007 (3%) | 17054 (55%) | 12783 (41%) | 30844 |

| 任务 | 开销倍数（tokens） | 耗时倍数 | 单 Agent 工具调用 | 多 Agent 工具调用 |
|------|------------------|---------|-----------------|-----------------|
| hello | **4.2×** | 6.1× | 4 | 10 |
| sales | **9.1×** | 8.3× | 3 | 19 |
| requirements | **5.2×** | 3.7× | 6 | 29 |

## 结论

### 1. 正确率没有提升，成本 4.2–9.1 倍

6 次运行里，状态机判定和独立产物验收**完全一致**，全部通过。
也就是说：这三个任务上，多 Agent 一个错误都没多拦住，纯粹是净开销。

这不是"架构错了"，是**任务选得不够难** —— 三个任务单 Agent 都能一次做对。
但它足以说明一件事：**多 Agent 不是默认更优解。**

顺带一个真实的反例：冒烟测试时用 `max_calls=12` 跑 `hello`，结果是

```
状态机判定 : failed   (llm_calls_exhausted 12/12)
产物验收   : PASS     (hello.txt 内容正确)
两者一致   : False
```

任务其实做完了，但 Planner 把一个 1 步任务拆成 4 步，预算在走完流程前就烧完了。
**"状态机说失败"和"任务失败"是两件事** —— 这也是为什么必须有两套口径。

### 2. Planner 不是成本大头（3–5%）

一次规划调用：输入约 250 tokens（只有目标，没有别的上下文），输出 600–700 tokens。
和"规划很贵"的直觉相反。

原因很朴素：**Planner 的上下文是最干净的**。它看不到任何文件内容，
也看不到中间过程，prompt 里只有一个目标字符串和一段格式要求。
它是整条链路里唯一一个"输入比输出小"的角色。

### 3. 评估成本 ≈ 执行成本（最反直觉的一条）

- `hello`：evaluator 8833 > executor 7280（**评估比执行还贵**）
- `sales`：11810 vs 12679
- `requirements`：12783 vs 17054

平均下来，评估吃掉总成本的 41%–52%。

原因不是"评估器啰嗦"，而是**它真的在独立核验**：
Executor 读过的东西，Evaluator 要自己再读一遍才能确认。
`sales` 那次评估器每步都用 `list_files` + `read_file` 重新打开产物核对数字。

这是"独立验证"的真实价格。想要它，就得付；不想要，那 Evaluator 就只剩橡皮图章，
不如直接删掉。**没有"便宜的独立验证"这种东西。**

### 4. 每一步至少 4 次 LLM 调用

Executor 的一次"步骤"永远是两轮：先调工具，再汇报。
Evaluator 是两到三轮：先 `list_files`，再 `read_file`，最后给判定。

实测 `hello`：16 次调用 / 4 步 = **每步 4 次**。
`max_llm_calls=30` 看起来很宽裕，实际上只够 5–6 个步骤。

### 5. 单 Agent 赢的真正原因：并行工具调用

`requirements` 任务里单 Agent 的第一次调用，工具列表是：

```
tools=[list_files, read_file, read_file, read_file]     <- 一轮读完 3 个来源文件
```

第二次调用：

```
tools=[write_file, write_file]                          <- 一轮写完 2 个产物
```

三次调用，6 次工具调用，任务结束。

多 Agent 把同一件事拆成 4 步串行，每步的 Executor 和 Evaluator **各自重新读一遍**：

```
工具调用 6 次 -> 29 次
```

**架构差异不在"发了几次 LLM 请求"，而在"能不能把 N 个动作压进一轮"。**
多 Agent 的状态机天然是串行的（步骤之间要判裁决），
它主动放弃了单 Agent 手里最有效的那个杠杆。

### 6. 上下文裁剪的收益是真的，但还没到兑现的规模

`requirements` 任务的 prompt token 走势：

```
solo     :  596 ->  997 -> 2505     最后/最初 = 4.2x
multi    :  每步重置
  exec step1:  956 -> 1060
  exec step2: 1053 -> 1414
  exec step3: 1278 -> 1715 -> 1873
  exec step4: 1386 -> 1848 -> 2519
```

多 Agent 确实把增长限制在单步内，每步开头都会掉回 1000 左右。
但在**这个任务规模上，两者的最大 prompt 几乎一样**（2505 vs 2519）。

裁剪优势要到"几十步 / 几十个文件"才会显现。三个任务都太短，
所以这条收益在这份数据里**没有被验证**，只是一个机制上的合理性。

## 那什么时候才值得拆？（假设，本章未验证）

按这份数据的逻辑外推，多 Agent 划算的条件至少要满足其中之一：

1. **工作集超过单窗口的舒适区** —— 单 Agent 每轮重发全部历史，长任务下 prompt 线性膨胀；
   多 Agent 每步上下文有上界。
2. **单个步骤的产物必须精确，且错误会累积** —— 这时独立核验的收益 > 它 40% 的成本占比。
3. **子任务可并行** —— 注意本章的状态机是纯串行的，没吃到并行的任何好处；
   这是当前实现最大的浪费点。
4. **权限边界是刚需** —— 生产里就是"执行 Agent 不能碰生产库""评审 Agent 不能改代码"。
   这时拆角色的理由不是准确率，是安全。
5. **需要审计轨迹** —— 每一步谁做的、依据是什么、被打回几次，都要留痕。

任务只要满足不了任何一条，**单 Agent 就是更优解**。

## 局限（别拿这份数据过度外推）

- **n=1**：每个组合只跑了一次。单次运行的 token 波动（主要来自模型的输出长度）没有均值化。
- **单模型**：只有 `deepseek-flash`。换更弱的模型，多 Agent 的分工收益可能变大；
  换更强的模型，单 Agent 可能更强。
- **任务规模偏小**：3–29 次工具调用。第 6 条结论里的"上下文裁剪"根本没被压到极限。
- **串行编排**：本章的状态机不做并行步骤，所以对比里少了一个本该属于多 Agent 的优势。
- **一笔可以省的钱**：Evaluator 的最后一次调用没有输出长度约束。
  `hello` 那次它为了给一句判定生成了 **1773 个 completion token**（占该次运行总量的 10.5%），
  而正常只需要几十个。给这个调用加 `max_tokens=200` 就能省掉，
  但改了就得重跑全部数据，所以这一章留作已知问题（见 README「未做的事」）。
